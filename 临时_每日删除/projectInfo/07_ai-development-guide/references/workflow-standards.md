# 流程规范 - 基于 Skills 的标准开发工作流

这是一个完整的开发流程，从需求分析到上线，展示了 AI 技能在各个阶段的应用。

## 工作流概览

```
需求分析 → 方案设计 → 代码开发 → 代码审查 → 测试回归 → 上线部署 → 监控告警
```

---

## 阶段 1：需求分析

**目标**：分析与拆解原始需求，形成结构化产品文档

**涉及技能**：
- `business_requirement_analysis` - 业务需求分析
- `user_story_mapping` - 用户故事映射
- `acceptance_criteria_writing` - 验收标准编写

**触发方式**：
- 手动：用户指令 `/开始需求分析`
- 自动：项目创建或新需求提交

**输入**：
- 原始需求描述（文本、邮件、文档）

**输出**：
- 产品需求文档（PRD）
- 用户故事列表
- 验收标准

**验证**：
- PRD 包含：目标、用户故事、验收标准
- 文档格式正确
- 无歧义表述

---

## 阶段 2：方案设计

**目标**：根据 PRD 进行技术方案、架构与 UI 设计

**涉及技能**：
- `technical_architecture_design` - 技术架构设计
- `frontend_framework_selection` - 前端框架选型
- `ui_ux_prototyping` - UI/UX 原型设计
- `api_contract_design` - API 接口契约设计

**触发方式**：
- 自动：PRD 通过审批后自动启动
- 条件：`requirement_analysis.outputs.prd_approved == true`

**输入**：
- PRD 文档
- 项目约束（技术栈、时间表）

**输出**：
- 技术设计方案
- 组件架构图
- API 接口文档（OpenAPI/Swagger）
- UI 原型或设计稿

**工具支持**：
- `draw.io` - 绘制架构图
- `swagger_editor` - 设计 API

---

## 阶段 3：代码开发

**目标**：基于技术方案进行具体编码实现

**涉及技能**：
- `component_development` - 组件开发
- `css_framework_styling` - CSS 框架样式编写
- `unit_test_writing` - 单元测试编写
- `code_view` - 通过 diff 进行代码审查
- `git_workflow` - Git 工作流操作

**触发方式**：
- 自动：设计方案通过审批后自动启动

**输入**：
- 技术设计方案
- 项目代码库

**输出**：
- 源代码（`src/` 目录）
- 单元测试代码
- Git 提交记录

**环境激活**：
- `project_eslint_rules` - 项目 ESLint 规则
- `project_coding_conventions` - 项目编码规范

**最佳实践**：
- 频繁提交（每个功能点一次）
- 编写清晰的提交信息
- 及时测试代码

---

## 阶段 4：代码审查

**目标**：对提交的代码进行质量、安全与规范审查

**涉及技能**：
- `static_code_analysis` - 静态代码分析
- `security_vulnerability_scan` - 安全漏洞扫描
- `performance_budget_check` - 性能预算检查
- `pull_request_review` - PR 审阅评论

**触发方式**：
- 事件驱动：Git 推送（仅特性分支）
- 事件：`git_push`
- 分支过滤：`feature/*`

**输入**：
- Git diff（提交差异）
- 提交信息
- 代码更改

**输出**：
- 代码审查报告（Markdown）
- 问题列表（JSON）
- 自动创建 Issue（可选）

**质量门禁**：
- ❌ 阻塞性问题数：0
- 👤 审批人数：至少 1 人
- ✅ 通过后才能进入下一阶段

**检查项**：
- 代码规范（ESLint）
- 类型检查（TypeScript）
- 注释完整性
- 安全性检查（XSS、CSRF 等）
- 性能问题
- 代码重复率

---

## 阶段 5：测试回归

**目标**：在类生产环境中运行完整的自动化测试套件

**涉及技能**：
- `e2e_testing` - 端到端测试
- `integration_testing` - 集成测试
- `performance_testing` - 性能测试（Lighthouse）
- `visual_regression_testing` - 视觉回归测试

**触发方式**：
- 自动：代码审查通过后自动启动
- 条件：`code_review.outputs.review_passed == true`

**输入**：
- 源代码
- Staging 环境地址
- 测试用例

**输出**：
- 自动化测试报告（HTML）
- 性能分析报告（JSON）
- 测试覆盖率报告（LCOV）

**质量门禁**：
- ✅ E2E 测试通过率：100%
- ⚡ 性能分数：≥ 90
- 📊 代码覆盖率：≥ 80%

**测试范围**：
- 单元测试（开发阶段已完成）
- 集成测试（跨模块交互）
- E2E 测试（完整用户流程）
- 视觉回归（UI 一致性）
- 性能测试（加载时间、内存）

---

## 阶段 6：上线部署

**目标**：执行部署到生产环境，并进行上线后验证

**涉及技能**：
- `ci_cd_pipeline_management` - CI/CD 流水线管理
- `canary_deployment` - 金丝雀发布
- `health_check_monitoring` - 健康检查与监控
- `rollback_procedure` - 回滚流程

**触发方式**：
- 手动：需要人工确认
- 条件：`test_regression.outputs.all_passed == true`
- 需要批准

**输入**：
- 版本号
- 部署目标环境

**输出**：
- 部署成功记录（日志）
- 上线后健康状态（仪表板链接）
- 版本发布说明

**部署策略**：
- 金丝雀发布：先发布到 5% 的用户
- 灰度发布：逐步增加到 100%
- 可随时回滚

**上线后监控**：
- 监控时间：1 小时
- 监控指标：
  - 错误率
  - 响应时间
  - 服务可用性
  - 用户反馈

## 流程中的关键决策点

### 1. 需求是否清晰？
- **是** → 进入方案设计
- **否** → 返回需求分析，澄清需求

### 2. 设计方案是否合理？
- **是** → 进入代码开发
- **否** → 回到方案设计，重新设计

### 3. 代码审查是否通过？
- **是** → 进入测试回归
- **否** → 开发者修改代码，重新提交

### 4. 测试是否全部通过？
- **是** → 进入上线部署
- **否** → 开发者修复 Bug，重新测试

### 5. 部署是否成功？
- **是** → 完成，进入监控阶段
- **否** → 执行回滚，分析原因

## 并行执行的可能性

### 可以并行进行的工作：
- 前端开发和后端 API 开发（基于设计的 API 契约）
- 不同功能模块的开发
- 单元测试和集成测试

### 不能并行进行的工作：
- 需求分析和方案设计（需要输入输出依赖）
- 代码审查和开发（相互依赖）
- 测试和部署（需要测试通过）

## 通知和协作

### 阶段开始时
- 通知相关人员
- 发送任务清单

### 阶段完成时
- 生成总结报告
- 通知下一个接力人员

### 出现问题时
- 创建 Issue
- 通知技术负责人

### 工作流完成时
- 生成完整报告
- 归档所有输出
- 清理临时文件

## 度量和优化

### 关键指标
- 各阶段平均耗时
- 审查中发现的问题数
- 测试覆盖率
- 部署频率和成功率

### 定期审视
- 周度工作流统计
- 月度性能分析
- 季度流程优化

## 常见问题

**Q: 流程中的哪个环节最容易出问题？**
A: 通常是代码审查和测试阶段，因为需要高度的质量把控。

**Q: 可以跳过某些阶段吗？**
A: 不建议，除非是紧急 Hotfix。即使是 Hotfix，也应该完整地走完整个流程。

**Q: 如何加快流程速度？**
A: 并行执行可并行的工作，优化测试时间，改进工具链。
