## 第一章：问题诊断

### 📌 为什么你的 SKILL.md 不够用？

在 Skills 越来越火热的当下，很多人开始遇到这些问题：

> [!question] 常见困惑
> - 为什么我的 SKILL.md 写的那么长，反而感觉它越来越笨了？
> - 别人的 Skill 为什么有一大堆 Rules？
> - 如何做出特别厉害的 Skill？

### 🚨 单文件思维的两大困境

#### 困境一：上下文的"无形枷锁"

**问题描述**：把所有东西都塞进 SKILL.md 中

```
SKILL.md (太重了)
├── 全部指令
├── 全部规则
├── 全部示例代码
└── 全部参考文档
```

**带来的后果**：

| 后果 | 表现 |
|-----|------|
| **性能下降** | 加载和处理变慢，交互迟钝 |
| **关键信息丢失** | 上下文接近极限时，模型"遗忘"开头或中间的指令（指令漂移） |
| **预算超支** | 计费模式下，更大的上下文=更高成本 |

#### 困境二：维护的"噩梦迷宫"

**问题描述**：超过 500 行的 SKILL.md 很难维护

**带来的后果**：

```
┌─────────────────────────┐
│ 500+ 行 SKILL.md        │
│                         │
│ 修改时的痛点：         │
│ ❌ 逻辑混乱            │
│ ❌ 可读性差            │
│ ❌ 修改风险高          │
└─────────────────────────┘
```

## 第二章：核心方案

### 🎯 Skill 2.0 的核心思想：模块化与渐进式披露

#### 核心理念

```
SKILL.md 的新角色：
┌──────────────────┐
│   轻量的"目录"    │
│  （Progressive   │
│  Disclosure）    │
└──────────────────┘
         ↓
    按需读取各种文件：
    ✅ rules/
    ✅ workflow/
    ✅ templates/
    ✅ config/
```

> [!success] 类比理解
> 就像阅读一本书：
> 1. **先看目录（SKILL.md）**：浏览全书结构
> 2. **按需阅读章节**：对某个章节感兴趣时，才翻到那一页
>
> Claude 使用 Skill 完全相同！不会一口气吞下所有信息，而是先加载轻量的"目录"，然后根据任务需要，通过文件链接去"翻阅"具体的"章节"。

### 📐 文档架构的核心规则

#### 唯一强制要求：SKILL.md

```plaintext
my-skill/
└── SKILL.md    ← 这是唯一强制要求的文件
```

> [!danger] 重要
> 没有 `SKILL.md`，Claude 不会识别这个目录为 Skill。

#### 其他文件和文件夹：完全自由

```plaintext
my-skill/
├── SKILL.md                 # 强制
├── 随便叫什么/              # 可选，自由命名
│   └── 任意文件.md
├── abc.json                 # 可选，自由
├── 中文文件夹/              # 可选，支持中文
│   └── 说明.txt
└── scripts/                 # 可选，自由
    └── helper.py
```

> [!warning] 关键提示
> **Claude 不会自动读取这些文件！**
> 你需要在 `SKILL.md` 中明确告诉 Claude 这些文件的存在和用途。

### 🏗️ 两种核心架构模式

#### 模式一：知识库型（Knowledge Base）

**适用场景**：Skill 主要为 Claude 提供**静态、结构化的知识**

| 例子 | 说明 |
|-----|-----|
| 公司内部 API 文档 | 开发人员查阅 |
| 编程框架最佳实践 | React、Vue 等 |
| 团队设计规范 | 写作风格指南 |

**核心理念**：**将知识"原子化"**
- 每个独立知识点 = 独立文件
- SKILL.md = 这些知识点的"索引"或"目录"

**目录结构**：

```plaintext
📁 company-knowledge/
├── 📄 SKILL.md              ← 核心入口：知识索引
└── 📁 knowledge/            # 规则目录（可自由命名）
    ├── 📄 术语表.md         # 知识点1
    ├── 📄 产品FAQ.md        # 知识点2
    ├── 📄 报销流程.md       # 知识点3
    └── 📁 assets/           # (可选) 代码示例或图片
         └── xxx.tsx
```

**SKILL.md 示例**：

```markdown
---
name: company-knowledge
description: 公司内部知识库。了解公司术语、产品信息或内部流程时使用。
---

# 公司知识库

- **术语表**：公司常用专业术语 → [knowledge/术语表.md](knowledge/术语表.md)
- **产品FAQ**：产品常见问题解答 → [knowledge/产品FAQ.md](knowledge/产品FAQ.md)
- **报销流程**：费用报销详细步骤 → [knowledge/报销流程.md](knowledge/报销流程.md)

请根据用户的问题，查阅对应的知识文件。
```

**工作原理**：

```
用户问："公司的 OKR 是什么意思"
         ↓
Claude 看 SKILL.md，发现这是术语问题
         ↓
打开 knowledge/术语表.md，找到 OKR 解释
         ↓
回答用户

💡 关键：Claude 不会打开"产品FAQ"或"报销流程"，因为跟当前问题无关
   这就是"按需取用"的威力！
```

> [!danger] 重要原则
> 如果 SKILL.md 里面没有提及某些文件，**那些文件将永远不会被用上**！

---

#### 模式二：工作流型（Workflow）

**适用场景**：Skill 要完成**多步骤的任务**

| 例子 | 步骤 |
|-----|------|
| **写周报** | 收集信息 → 整理 → 输出 |
| **会议纪要** | 听录音 → 提取要点 → 生成文档 |
| **发布文章** | 检查格式 → 配图 → 发布 |

**核心理念**：**将任务"流程化"**
- 复杂任务 → 一系列线性、可独立执行的步骤
- 每个步骤 = 独立文件

**推荐目录结构**：

```plaintext
📁 weekly-report/
├── 📄 SKILL.md              ← 总指挥
├── 📁 workflow/             # 流程步骤
│   ├── 📄 step1-收集信息.md   # 步骤1
│   ├── 📄 step2-整理内容.md   # 步骤2
│   └── 📄 step3-生成周报.md   # 步骤3
├── 📁 templates/            # 参考模板
│   └── 📄 周报模板.md
└── 📁 rules/                # 规范要求
    └── 📄 写作规范.md
```

**SKILL.md 示例**：

```markdown
---
name: weekly-report
description: 自动生成周报。当用户说"写周报"、"生成本周总结"时触发。
---

# 周报生成助手

请严格按照以下步骤执行：

## 执行清单

- [ ] 第一步：收集信息 → [workflow/step1-收集信息.md](workflow/step1-收集信息.md)
- [ ] 第二步：整理内容 → [workflow/step2-整理内容.md](workflow/step2-整理内容.md)
- [ ] 第三步：生成周报 → [workflow/step3-生成周报.md](workflow/step3-生成周报.md)

## 参考资料

- 周报格式：[templates/周报模板.md](templates/周报模板.md)
- 写作要求：[rules/写作规范.md](rules/写作规范.md)
```

**工作原理**：

```
用户："帮我写周报"
      ↓
Claude 看 SKILL.md，了解整体流程
      ↓
依次执行：
  step1（收集信息）
    ↓
  step2（整理内容）
    ↓
  step3（生成周报）
      ↓
在 step3 中，打开"周报模板"来格式化输出
      ↓
清单上每步都打勾 ✓

结果：像一条流水线，每个步骤清清楚楚，不会漏，不会乱！
```

---

### 📊 知识库 vs. 工作流：如何选择？

| 维度 | 知识库型 | 工作流型 |
|-----|---------|---------|
| **适用场景** | 静态、结构化知识 | 多步骤的任务流程 |
| **核心结构** | 知识点分散存储 | 步骤线性连接 |
| **文件关系** | 互相独立，按需调用 | 有严格的前后顺序 |
| **典型例子** | 公司手册、API文档 | 周报、会议纪要 |
| **组织方式** | 目录 + 索引 | 流程图 + 检查清单 |

> [!tip] 现实情况
> 这两种模式并非完全互斥。在工作流型 Skill 中，你完全可以引入 reference/ 目录来存放知识库型的参考文档。

#### 📝 步骤 2：编写"写作规范"（Rules）

**文件位置**：`rules/writing-guide.md`

```markdown
# 周报写作规范

## 语言风格
- 简洁、专业，避免口语化
- 多用数据和事实，少用模糊形容词
- 每个要点控制在 1-2 句话

## 内容要求
### ✅ 应该包含
- 本周完成的具体工作（带量化结果更好）
- 遇到的问题及解决方案
- 下周的工作计划

### ❌ 不要包含
- 流水账式的日常琐事
- 没有结论的问题描述
- 与工作无关的内容

## 格式要求
- 使用 Markdown 格式
- 重点内容用**加粗**标注
- 列表项不超过 5 条
```

#### 📄 步骤 3：编写"周报模板"

**文件位置**：`templates/report-template.md`

```markdown
# 周报 | {姓名} | {日期范围}

## 📌 本周概要
> 用 1-2 句话总结本周最重要的成果

## ✅ 完成事项
### {项目/模块名称 1}
- 具体完成的工作内容
- 量化成果（如有）

### {项目/模块名称 2}
- 具体完成的工作内容

## 🚧 进行中
- 正在进行但未完成的工作
- 预计完成时间

## ❗ 问题与风险
| 问题描述 | 影响范围 | 解决方案/需要的支持 |
| 问题1 | 影响1 | 方案1 |

## 📅 下周计划
- [ ] 计划事项 1
- [ ] 计划事项 2
- [ ] 计划事项 3
```

#### 🔄 步骤 4：编写工作流步骤

**文件 1**：`workflow/step1-collect.md`

```markdown
# 第一步：收集本周工作信息

## 你的任务
向用户收集以下信息：

1. **本周完成了哪些工作？**
   - 参加的会议、提交的成果、解决的问题

2. **有没有遇到困难或阻碍？**

3. **下周有什么计划？**

## 收集技巧
- 如果用户回答太简略，追问细节
- 如果用户回答太啰嗦，帮他提炼重点

## 完成标志
当你收集到足够的信息后，进入下一步。
```

**文件 2**：`workflow/step2-organize.md`

```markdown
# 第二步：整理和分类

## 你的任务
将收集到的信息进行整理：

1. **分类**：按项目或模块分组
2. **提炼**：把啰嗦的描述精简成 1-2 句话
3. **量化**：尽可能加上数据
4. **排序**：重要的放前面

## 参考标准
整理时请参考 [rules/writing-guide.md](../rules/writing-guide.md) 中的写作规范。

## 完成标志
你应该有一份结构清晰的内容大纲。
```

**文件 3**：`workflow/step3-generate.md`

```markdown
# 第三步：生成最终周报

## 你的任务
1. 打开 [templates/report-template.md](../templates/report-template.md)
2. 将整理好的内容填入模板
3. 检查格式是否正确
4. 输出最终周报

## 输出要求
- 直接输出 Markdown 格式的周报
- 不要输出任何解释性文字
- 确保所有占位符（如 {姓名}）都已替换

## 完成！
输出周报后，询问用户是否需要修改。
```

## 第四章：进阶技巧

### 🔥 三个让 Skill 更强大的进阶技巧

#### 技巧一：用配置文件实现"一键切换"

**场景**：不同部门的周报格式要求不同

**目录结构**：

```plaintext
📁 weekly-report-ai/
├── 📄 SKILL.md
├── 📁 config/
│   ├── 📄 tech-team.json      ← 技术部配置
│   └── 📄 marketing-team.json  ← 市场部配置
└── ...
```

**配置文件示例** (`config/tech-team.json`)：

```json
{
  "team_name": "技术部",
  "focus_areas": ["代码提交", "Bug修复", "技术方案"],
  "report_style": "数据导向，多用指标"
}
```

**在 SKILL.md 中引用**：

```markdown
请先读取 `config/tech-team.json`，了解本次周报的特殊要求。
```

> [!important] 关键
> 必须在 SKILL.md 中引用文件，否则不会生效！

---

#### 技巧二：用"禁止清单"防止 Claude 犯错

**场景**：告诉 Claude "不要做什么" 比 "要做什么" 更有效

**文件位置**：`rules/dont-do.md`

```markdown
# 🚫 禁止事项

以下行为是**绝对禁止**的：

1. **禁止编造**：不要编造用户没有提到的工作内容
2. **禁止使用表情**：周报是正式文档，不要用 emoji
3. **禁止超长段落**：单个段落不超过 3 句话
4. **禁止模糊表达**：不要用"一些"、"若干"、"大概"等词
```

**在 SKILL.md 中强调**：

```markdown
⚠️ 执行前，请务必阅读 [rules/dont-do.md](rules/dont-do.md) 中的禁止事项！
```

---

#### 技巧三：用"检查清单"确保质量

**方法**：在最后一步加一个自检环节

**文件位置**：`workflow/step4-review.md`

```markdown
# 第四步：输出前自检

在输出最终周报之前，请逐项检查：

- [ ] 格式是否符合模板要求？
- [ ] 是否有错别字或语法错误？
- [ ] 数据和事实是否准确（没有编造）？
- [ ] 是否违反了禁止清单中的任何一条？
- [ ] 内容是否简洁（没有废话）？

**全部通过后，再输出周报。**
```

> [!tip] 效果
> 这就像给 Claude 配了一个"质检员"，大大减少低级错误。
