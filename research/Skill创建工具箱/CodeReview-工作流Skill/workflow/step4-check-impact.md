# 第四步：检查影响

代码改动会不会对其他功能造成影响或风险。

---

## 🎯 这一步的目的

- 识别潜在的副作用
- 发现兼容性问题
- 评估改动的影响范围
- 防止引入新的 bug

---

## 📝 需要检查的内容

### 1. 依赖关系

- [ ] 这个模块被谁调用？（有其他地方依赖这个模块吗）
- [ ] 改动了什么接口/API？（是否改变了函数签名）
- [ ] 是否破坏了后向兼容性？（会不会影响其他使用者）
- [ ] 相关的模块需要同步改动吗？
- [ ] 是否需要更新导出的接口？

### 2. 测试覆盖

- [ ] 有没有新增或修改的测试？
- [ ] 测试是否覆盖了改动的代码？
- [ ] 现有的测试会不会失败？
- [ ] 测试覆盖率是否合理？
- [ ] 是否需要添加集成测试？

### 3. 性能影响

- [ ] 改动会影响性能吗？
- [ ] 加载时间会增加吗？
- [ ] 内存占用会增加吗？
- [ ] 是否有优化空间？
- [ ] 大规模数据下是否仍然高效？

### 4. 安全影响

- [ ] 有没有新引入的安全风险？
- [ ] 用户输入是否都验证了？
- [ ] 敏感信息是否保护好了？
- [ ] 有没有 XSS、SQL 注入等风险？
- [ ] 权限检查是否完整？

### 5. 其他影响

- [ ] 文档需要更新吗？
- [ ] API 文档需要更新吗？
- [ ] 数据库 schema 需要改动吗？
- [ ] 部署流程需要特殊处理吗？
- [ ] 有回滚计划吗？
- [ ] 是否需要数据迁移？

---

## 🚩 发现风险？

如果发现潜在的风险或影响：

1. **风险描述** - 说明风险是什么
2. **受影响范围** - 哪些功能、模块、用户可能受影响
3. **严重程度** - 这个风险有多严重
4. **建议** - 如何规避或解决

**示例：**
```
【风险】改动了用户数据结构
影响范围：所有使用 User 模型的地方
受影响功能：登录、个人资料、权限检查等
建议：需要数据迁移脚本，并向数据库发起 schema 变更请求
```

---

## ✅ 安全检查清单

- [ ] 没有硬编码密钥或密码
- [ ] 没有暴露内部实现细节
- [ ] 没有信息泄露风险
- [ ] 权限检查完整
- [ ] 输入验证充分
