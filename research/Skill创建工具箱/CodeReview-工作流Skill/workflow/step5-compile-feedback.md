# 第五步：整理反馈

把审查过程中发现的问题汇总成反馈意见。

---

## 🎯 这一步的目的

- 清晰地总结审查结果
- 给出建设性的改进建议
- 帮助 author 快速理解反馈
- 指导后续的改动

---

## 📝 反馈的组织方式

### 1️⃣ 整体评价

先给出总体的评价：

- **✅ 代码质量很好** - 符合规范，逻辑清晰，可以合并
- **⚠️ 有一些需要改进的地方** - 有小问题，建议修改后合并
- **❌ 有较多问题** - 需要重新审视整体设计或实现

**然后简述主要原因：**
```
[1-2 句话说明你的整体评价]
```

---

### 2️⃣ 分类总结

按照严重程度分类列出所有问题和建议：

#### 🔴 Blocking（需要修改后才能合并）

这些是必须修改的问题：

```
【问题 1】[标题]
- 文件位置：xxx.tsx, 第 XX 行
- 问题描述：[详细描述]
- 为什么重要：[说明影响]
- 修改建议：[给出改进方案]
- 参考：[知识库链接]

【问题 2】[标题]
...
```

#### 🟡 Warning（应该修改）

这些是建议修改的地方：

```
【建议 1】[标题]
- 文件位置：xxx.tsx, 第 XX 行
- 建议：[说明建议是什么]
- 为什么更好：[解释这样做的好处]

【建议 2】[标题]
...
```

#### 🟢 Info（参考信息）

这些是参考信息，可选修改：

```
- [参考信息 1]
- [参考信息 2]
```

---

### 3️⃣ 优点（可选）

列出代码的优点，鼓励 author：

```
✅ [值得表扬的地方 1]
✅ [值得表扬的地方 2]
```

## 💡 反馈原则

在整理反馈时，记住这些原则：

- ✅ **具体** - 说明具体问题在哪，不要模糊
- ✅ **建设性** - 不仅指出问题，还给出改进建议
- ✅ **尊重** - 用友好和尊重的语气，不要讽刺或责备
- ✅ **有根据** - 引用规范或最佳实践，让 author 容易接受
- ✅ **有优先级** - 区分 🔴 Blocking 和 🟡 Warning，帮助 author 安排修改顺序

---

## 🎯 反馈例子

### 好的反馈 ✅

```
【问题】变量命名不清晰

位置：UserProfile.tsx, 第 25 行

当前代码：
const d = userData

问题：变量名 d 太简洁，不容易理解这是什么数据

建议：改为更清晰的名称
const userProfileData = userData
或
const currentUser = userData

参考：知识库 > 命名规范 > 变量命名
```

### 不好的反馈 ❌

```
这里的变量名不好，改一下
```

---

## ✅ 发布前检查

整理反馈时，检查以下内容：

- [ ] 整体评价清晰
- [ ] 所有问题都有具体位置
- [ ] 所有建议都有改进方案
- [ ] 问题分级正确
- [ ] 语气友善和建设性
- [ ] 引用了相关规范或最佳实践
- [ ] 没有拼写错误

---

## 🔄 反馈后的流程

反馈发布后：

1. Author 根据反馈修改代码
2. Author 请求重新审查
3. 你根据修改情况再次审查
4. 确认所有 🔴 Blocking 问题都解决了
5. 代码可以合并
