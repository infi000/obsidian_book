# 反馈撰写原则

---

## 好反馈的 5 个特点

### ✅ 具体

说明具体的问题在哪，不要模糊。

**❌ 坏的例子：**
```
这里代码写得不好
```

**✅ 好的例子：**
```
这里的变量 `d` 命名不清晰，建议改为 `userProfileData` 以提高可读性
位置：UserProfile.tsx, 第 25 行
```

### ✅ 建设性

不仅指出问题，还给出改进建议。

**❌ 坏的例子：**
```
这里有 bug
```

**✅ 好的例子：**
```
这里没有处理 API 失败的情况。建议添加 try-catch：

try {
  const data = await fetchUser(id)
  setUser(data)
} catch (err) {
  setError(err.message)
}
```

### ✅ 尊重

用友好和尊重的语气，不要讽刺或责备。

**❌ 坏的例子：**
```
这都不会写吗？
```

**✅ 好的例子：**
```
这里可能需要考虑空值情况。如果 user 是 null，会导致错误。
建议添加检查：if (user) { ... }
```

### ✅ 有根据

引用规范或最佳实践，让 author 容易接受。

**❌ 坏的例子：**
```
改一下这里
```

**✅ 好的例子：**
```
根据我们的代码规范，函数应该控制在 15 行以内。
这个函数有 30 行，建议拆分成两个函数。
参考：知识库 > 代码规范 > 函数长度
```

### ✅ 有优先级

区分 🔴 Blocking 和 🟡 Warning，帮助 author 安排修改顺序。

**❌ 坏的例子：**
```
有很多问题...
```

**✅ 好的例子：**
```
🔴 Blocking：处理 API 失败
🟡 Warning：优化变量命名
🟢 Info：考虑添加缓存
```

## 反馈模板

**推荐的反馈结构：**

```markdown
### 📊 整体评价

[✅ 好 / ⚠️ 一般 / ❌ 差]

主要原因：[1-2 句话]

---

### 🔴 Blocking（必须修改）

#### 问题 1：[标题]
- 位置：[文件路径, 第 XX 行]
- 问题：[具体描述问题]
- 建议：[改进方案]
- 参考：[规范链接]

---

### 🟡 Warning（应该修改）

#### 建议 1：[标题]
- 位置：[文件路径, 第 XX 行]
- 建议：[具体建议]
- 原因：[为什么这样做更好]

---

### 🟢 Info（参考信息）

- [参考信息 1]
- [参考信息 2]

---

### ✅ 优点

- [值得表扬的地方 1]
- [值得表扬的地方 2]

---

### 📝 下一步

- [ ] 解决所有 🔴 问题
- [ ] 处理 🟡 建议
- [ ] 考虑 🟢 信息
```

## 反馈措辞建议

### 描述问题时

- 使用"我建议..."而不是"你应该..."
- 使用"可以考虑..."而不是"必须..."
- 说明问题的具体影响

**例如：**
```
我建议这里添加错误处理，因为网络请求可能失败，导致用户看到白屏。
```

### 给出建议时

- 提供具体的代码示例
- 解释为什么这样做更好
- 承认可能有多种解决方案

**例如：**
```
建议改为这样：
```typescript
const [loading, setLoading] = useState(false)
const [error, setError] = useState(null)

try {
  setLoading(true)
  const data = await fetchUser(id)
  setUser(data)
} catch (err) {
  setError(err.message)
} finally {
  setLoading(false)
}
```

这样做的好处是用户能看到加载状态和错误提示。
```

### 鼓励时

- 具体说明做得好的地方
- 说明为什么这是好的做法

**例如：**
```
✅ 很好的是你添加了完整的错误处理和加载状态，
这会大大改善用户体验。
```

## 常见的反馈错误 ❌

- ❌ 反馈太长，author 看不完
- ❌ 反馈太模糊，author 不知道改什么
- ❌ 反馈都是 Blocking，没有 Warning
- ❌ 反馈太严厉，伤害 author 的积极性
- ❌ 反馈没有根据，author 难以接受
- ❌ 反馈没有建议，只有问题
