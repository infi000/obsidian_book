# Step 1: 理解上下文

Code Review 的第一步是**理解这个 PR 在做什么**，而不是一上来就看代码。

⏱️ **预期时间：5 分钟**

## 🎯 目标

在这一步，你需要：
- ✅ 理解 PR 想解决什么问题
- ✅ 理解改动的范围
- ✅ 识别可能受影响的部分
- ✅ 判断自己是否适合审查这个 PR

## 📋 检查清单

### 1. 读 PR 标题和描述

- [ ] PR 标题清晰吗？（应该遵循[[../../知识库型Skill/standards/git-workflow|Git 规范]]）
- [ ] PR 描述说明了为什么要做这个改动吗？
- [ ] 关联了相关的 Issue 吗？（Fixes #123）

**问题示例**：
- ❌ "fix: bug" - 太模糊
- ✅ "fix: fix button click handler not working on mobile" - 清晰

### 2. 理解业务背景

- [ ] 我理解这个功能要做什么吗？
- [ ] 这个改动会影响哪些用户或功能？
- [ ] 有什么业务限制或特殊要求吗？

**建议**：
- 如果不理解，问提交 PR 的同学
- 查看关联的 Issue 或需求文档

### 3. 快速浏览改动文件

- [ ] 改动了哪些文件？（看 "Files changed"）
- [ ] 改动的规模合理吗？（不应该太大）
- [ ] 有没有看起来不相关的文件？

**红旗信号**：
- 🚩 一个 PR 改动了 50+ 个文件 - 可能太大了
- 🚩 改动包含格式化或重构 - 应该分开
- 🚩 包含了不相关的文件 - 问问为什么

### 4. 识别关键代码

- [ ] 哪些代码是核心逻辑？
- [ ] 哪些是辅助代码？
- [ ] 哪些代码是我应该重点关注的？

**建议**：
- 先看主要改动，再看细节
- 关注业务逻辑，而不仅仅是代码风格

### 5. 判断自己是否能审查

- [ ] 我对这个代码领域熟悉吗？
- [ ] 我有足够的时间进行认真审查吗？
- [ ] 我需要请高级开发者帮助吗？

**判断标准**：
- ✅ 我理解相关的代码库
- ✅ 我有至少 20-30 分钟的时间
- ✅ 我对审查内容有信心

**如果回答 "不"**：
- 😕 告诉提交者你现在不能审查，他们应该找别人
- 😕 或者说你会在什么时候能够审查

## 📝 示例

### 好的 PR 描述

```markdown
feat(checkout): add discount code validation

## 问题
目前系统不验证优惠码，导致无效的优惠码也能被使用，造成收入损失。

## 解决方案
- 添加 DiscountCodeValidator 类
- 在结账时验证优惠码的有效性、过期时间、使用次数限制
- 如果无效，显示友好的错误提示

## 改动范围
- checkout/DiscountCodeValidator.ts (新文件)
- checkout/CheckoutForm.tsx (修改表单提交逻辑)
- types/discount.ts (添加类型定义)
- tests/DiscountCodeValidator.test.ts (新测试)

## 关联 Issue
Fixes #234

## 测试方式
1. 使用有效优惠码测试
2. 使用过期优惠码测试
3. 使用已用尽优惠码测试
4. 验证错误消息显示正确
```

### 不好的 PR 描述

```markdown
fix: various fixes and improvements
```

（太模糊，不知道改了什么）

## 🚨 需要停止审查的情况

如果出现以下情况，**停止审查，告诉提交者**：

1. **范围太大** - PR 改动了 200+ 行，应该分成多个 PR
2. **没有清晰描述** - 完全不知道为什么改这个
3. **混合了多个功能** - 应该分开多个 PR
4. **含有格式化或大重构** - 应该分开 PR
5. **你没有足够的领域知识** - 应该找专家审查

**怎么说**：
```
这个 PR 的范围太大了，建议分成几个更小的 PR：
1. 验证逻辑改动
2. UI 改动
3. 测试添加

这样会更容易审查，也更安全。
```

## ✅ 完成这一步后

如果你已经：
- ✅ 理解了 PR 的目的
- ✅ 知道改动了哪些部分
- ✅ 判断自己能够审查
