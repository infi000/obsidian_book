# AI Code Review 系统规格说明

## 1. 执行摘要

**问题陈述**：
在有30多人的开发团队中，管理十几套系统的代码审查是关键瓶颈。当前的人工CR流程耗时过长，尤其是对于比价大的系统。通用的AI Code Review工具无法理解项目特定的代码逻辑、内部组件使用规范、业务风险点，导致输出的建议信噪比低。

**核心需求**：
构建一个**项目感知型的 AI Code Review 系统**，能够基于项目代码库自动学习和维护规范知识库，在代码变更触发时进行智能化审查。该系统应该：
1. 自动从项目代码中提取和沉淀规范知识（REVIEW_STANDARDS.md）
2. 基于项目特定的规范进行代码审查
3. 识别人工审查容易发现的问题和人工审查容易遗漏的问题
4. 为开发者和审查者提供有价值的、低信噪比的建议

**成功定义**：
- 能够在PR提交或手动触发时进行自动化代码审查
- 生成的建议有80%以上的情报价值（不仅仅是低级错误，还包括业务逻辑风险）
- 规范知识库与代码库同步演进
- 支持项目特有的技术栈（React、Vue2、Vue3等）

|------|--------|--------|

## 3. 项目现状分析

### 3.1 项目规模与结构

**代码库规模**：
- 总代码文件数：~2,473 个 TypeScript/TSX 文件
- 项目年龄：有历史积累（多个版本演进痕迹）
- 核心目录结构：
  ```
  src/
  ├── components/       # 通用组件库（~80+ 组件目录）
  ├── containers/       # 业务模块（~150+ 业务场景）
  ├── hooks/           # 自定义 Hooks（6+ 个）
  ├── utils/           # 工具函数库
  ├── state/           # 全局状态管理
  ├── translations/    # 国际化
  └── ...
  ```

### 3.2 技术栈

**前端框架**：React 16.5.2 + Redux + Redux-Saga
**状态管理**：
- Redux + Immutable.js
- Redux-Saga 用于异步处理
- Connected-React-Router 用于路由状态同步

**样式**：
- Styled-components
- Less
- Ant Design v3.23.6

**构建工具**：
- Webpack 4 (主)
- Vite (新项目试用)

**TypeScript**：3.8.3（有类型覆盖）

### 3.3 代码组织模式

#### 容器（Container）模式
每个业务模块（如 AlarmRecord）遵循标准结构：
```
src/containers/AlarmRecord/
├── index.tsx              # 容器入口，compose HOC
├── reducer.tsx            # Redux reducer
├── saga.tsx               # 异步处理逻辑
├── actions.tsx            # Action creators
├── selectors.tsx          # Reselect selectors
├── constants.tsx          # 常量和命名空间
├── services.tsx           # API 调用
├── messages.tsx           # 国际化消息
├── types.ts               # TypeScript 类型定义
├── components/            # 本地组件
└── modules/               # 功能模块
```

#### Reducer 模式
- 使用 Immutable.js 管理状态不可变性
- 使用 `fromJS()` 包裹状态对象
- 使用 `set()` 和 `setIn()` 进行状态更新
- 监听 `${FATCH_ACTION_SUCCESS_PREFIX}${ACTION_NAME}` 的 action 格式

#### 组件连接模式
使用 Redux 的 compose + injectReducer + injectSaga HOC：
```typescript
compose(withRouter, withSaga, withReducer)(Component)
```

### 3.4 现有规范线索

**从代码中可见的规范**：
- 组件命名：PascalCase（组件），camelCase（文件）
- 常量：UPPER_SNAKE_CASE（在 constants.tsx）
- Action type：使用常量而非字符串字面量
- Selector：使用 createStructuredSelector 和 reselect
- 错误处理：使用 `FATCH_ACTION_SUCCESS_PREFIX` 前缀约定
- 状态初始化：使用 fromJS 包裹初始状态

**隐性知识**（散落在代码中）：
- 哪些组件不应该重复开发
- 自定义 hooks 的使用场景（useTableScrollX, useGetRequest等）
- 异步操作的标准流程（saga → action → reducer）
- 时间戳的使用约定（使用 moment().format('X')）

## 4. 详细需求（按维度组织）

### 4.1 知识库构建维度

#### 需求 4.1.1：自动生成 REVIEW_STANDARDS.md
**描述**：
系统应该主动分析当前项目代码库，自动生成一份 `REVIEW_STANDARDS.md` 文档，用于指导后续的 AI CR。

**具体内容应包括**：

1. **代码组织规范**
   - 目录结构约定（容器模式）
   - 文件命名规范
   - 组件组织方式

2. **技术栈使用规范**
   - Redux/Immutable.js 的标准用法
   - Saga 异步处理模式
   - Selector 编写规范
   - Hook 的使用规范

3. **常见模式识别**
   - 重复开发的组件清单
   - 相似的业务流程实现方式
   - 推荐使用的工具函数

4. **风险点和陷阱**
   - 容易出错的地方
   - 业务逻辑常见错误
   - 性能陷阱
   - 状态管理常见问题

5. **命名约定**
   - Action type 命名
   - Reducer state 键名约定
   - Selector 命名模式

**验收标准**：
- [ ] REVIEW_STANDARDS.md 存放在项目根目录
- [ ] 文档包含上述5类内容
- [ ] 文档基于实际代码分析生成（非通用模板）
- [ ] 文档长度 1000-3000 字，保持可阅读性

#### 需求 4.1.2：规范知识库的维护机制
**描述**：
随着项目演进，REVIEW_STANDARDS.md 需要定期更新，沉淀新的规范和最佳实践。

**具体需求**：
- 每次 CR 时，AI 可以记录发现的新模式或规范偏离
- 定期（或按需）更新 REVIEW_STANDARDS.md
- 保持文档的版本历史

**预留位置**：后续补充具体的更新策略

### 4.2 代码审查维度

#### 需求 4.2.1：PR 自动触发代码审查
**描述**：
当代码变更通过 PR 或手动指定分支与 master 的 diff 时，自动触发 AI CR。

**具体流程**：
1. 获取 PR 或 diff 的变更代码
2. 基于 REVIEW_STANDARDS.md 进行分析
3. 生成审查报告

**触发方式**：
- [ ] Git Hook 自动触发（PR 创建时）
- [ ] 手动触发（指定分支和对比分支）
- [ ] 支持 master 分支和其他分支的 diff 对比

#### 需求 4.2.2：审查覆盖维度
**描述**：
AI 应该在以下维度进行代码审查，不限于低级错误检查。

**覆盖维度**（优先级顺序）：

1. **业务逻辑风险（P0）**
   - 状态流转是否正确
   - 异步操作是否有错误处理
   - API 调用的时序是否正确
   - 业务约束是否被违反

2. **代码规范偏离（P0）**
   - 是否遵循项目已有的模式和约定
   - 命名是否符合规范
   - 文件组织是否正确
   - 组件组织是否合理

3. **重复开发检测（P1）**
   - 新增组件是否与现有组件功能重复
   - 新增逻辑是否与现有代码重复
   - 是否应该使用现有的工具函数/Hook

4. **性能和优化（P1）**
   - Redux selector 是否正确使用（避免频繁创建新对象）
   - Hook 的依赖数组是否正确
   - React 组件是否有不必要的重渲染
   - 是否有内存泄漏风险

5. **低级错误（P2）**
   - 类型错误
   - 语法错误
   - 明显的逻辑错误

#### 需求 4.2.3：审查输出格式
**描述**：
审查结果应以清晰、结构化的格式输出，便于开发者和 reviewer 快速定位和理解。

**输出格式**：
- Markdown 报告（推荐）
- 包含以下章节：
  - 总结（发现问题数、风险等级分布）
  - 关键问题（业务风险、规范严重偏离）
  - 常见模式偏离
  - 重复开发警告
  - 优化建议
  - 细节问题（可折叠）

**验收标准**：
- [ ] 每个问题包含：位置、原因、建议、严重级别
- [ ] 问题按严重级别排序
- [ ] 避免重复报告同类问题

### 4.3 系统理解维度

#### 需求 4.3.1：项目特定知识的理解
**描述**：
AI 应该理解项目特有的实现模式和决策，而不是基于通用的代码规范。

**具体包括**：

1. **组件使用规范**
   - src/components 下的各个组件何时使用
   - 组件的 Props 约定
   - 何时应该使用现有组件，何时需要新开发

2. **工具函数和 Hook**
   - src/utils 下各工具函数的用途
   - src/hooks 下各自定义 Hook 的使用场景
   - 何时应该创建新 Hook

3. **业务逻辑模式**
   - 常见的数据流模式
   - 状态同步的约定
   - 错误处理的标准流程

4. **项目历史决策**
   - 为什么某个地方采用特定的实现方式
   - 避免重复的过去教训

**验收标准**：
- [ ] AI 能识别代码中是否正确使用了现有组件
- [ ] AI 能建议使用现有 Hook 而不是重新开发
- [ ] AI 能识别与项目历史模式的偏离

---

### 4.4 实现技术维度

#### 需求 4.4.1：技术方案
**描述**：
系统应该能够理解项目代码并基于规范进行分析。

**技术选型确定**：

| 维度 | 选型 | 说明 |
|------|------|------|
| **AI 模型** | 公司提供的 Claude 代理 | 无需自建模型，利用现有能力 |
| **RAG 增强** | 先不用，后续可选 | 初期使用 REVIEW_STANDARDS.md 作为上下文注入 |
| **集成方式** | Git Hook + 独立工具 | 支持自动触发和手动触发；Reviewer 电脑安装 Claude Code |
| **知识库管理** | REVIEW_STANDARDS.md + Git 版本管理 | 版本跟随 git commit，历史可追溯 |
| **部署方式** | 内网部署 + Claude API | 成本可控，无跨项目额外成本 |
| **性能需求** | 异步处理，无严格时间限制 | PR CR 可异步完成 |

**集成架构**（待详细设计）：
```
开发者提交代码
    ↓
Git Hook 触发（或手动用 Claude Code）
    ↓
读取 REVIEW_STANDARDS.md（项目规范）
    ↓
调用 Claude 代理进行分析
    ↓
生成 Markdown 审查报告
    ↓
返回 Reviewer / 开发者
```

#### 需求 4.4.2：支持多技术栈
**描述**：
虽然当前试点项目是 React，但系统应该可复用到 Vue2/Vue3 项目。

**设计原则**：
- 核心 CR 逻辑与框架无关
- 框架特定的规范单独维护
- REVIEW_STANDARDS.md 的模板可适配不同框架

## 5. 验收标准（明确、可测试）

### 5.1 功能验收标准

#### Criterion 1: REVIEW_STANDARDS.md 生成与质量
- [ ] 文档自动生成，无需手工编写
- [ ] 文档基于实际代码分析（不是通用模板）
- [ ] 包含组织规范、技术栈用法、常见模式、风险点、命名约定

- [ ] 支持 Git Hook 自动触发（PR 创建时）
- [ ] 支持命令行手动触发（指定分支）
- [ ] 支持与 master 的 diff 对比
- [ ] 触发结果能在合理时间内返回（异步可接受）

#### Criterion 3: 审查覆盖维度完整性
- [ ] 业务逻辑风险检测工作
- [ ] 代码规范偏离检测工作
- [ ] 重复开发检测工作
- [ ] 性能优化建议工作
- [ ] 低级错误检测工作

#### Criterion 4: 审查输出质量
- [ ] 输出清晰、结构化（Markdown 或诊断格式）
- [ ] 每个问题都有位置、原因、建议、级别
- [ ] 问题按优先级排序
- [ ] 避免虚假警告（噪音控制）
- [ ] 信息密度高（用户可快速定位有价值的建议）

#### Criterion 5: 项目特定知识理解
- [ ] 能识别现有组件的正确/错误使用
- [ ] 能建议复用现有 Hook 而非重复开发

#### Performance
- 代码审查响应时间：< 5 分钟（异步触发）
- 知识库更新时间：< 1 分钟

#### Reliability
- 无崩溃（处理各种代码异常）
- 知识库持久化（可恢复）

#### Usability
- 规范知识库易于维护和更新
- 审查报告易于理解和行动
- 集成成本低（对开发流程的干扰最小）

## 7. 关键风险与缓解方案

| 风险 | 影响 | 缓解方案 |
|------|------|--------|
| AI 理解有误 | 误报率高，降低工具信誉 | 初期设置高置信度阈值，持续调优 |
| 知识库不准确 | CR 建议不符合项目实际 | 人工审核首版规范，定期更新 |
| 集成复杂 | 部署和维护成本高 | 简化集成方式，提供清晰文档 |
| 性能不足 | 开发流程卡顿 | 异步处理，缓存结果 |
| 团队接受度 | 不愿使用工具 | 从试点项目建立信心，逐步推广 |

## 10. 已确认的关键决策

### 10.1 AI 模型选择
- ✅ **决策**：使用公司提供的 Claude 代理
- 无需自建模型，充分利用现有 AI 能力
- RAG 增强暂不使用，初期使用 REVIEW_STANDARDS.md 注入上下文
- **后续**：如果需要更强的知识库集成，可评估 RAG 方案

### 10.2 集成方式
- ✅ **决策**：Git Hook + 独立工具并行支持
- **Git Hook**：PR 自动触发，无感集成
- **独立工具**：Reviewer 电脑安装 Claude Code，手动触发
- 灵活支持不同工作流（自动化优先，手动兜底）

### 10.3 规范维护流程
- ✅ **决策**：AI 自动更新，每次 CR 后给出更新建议
- REVIEW_STANDARDS.md 跟随 git 版本管理
- 版本历史自动保存在 git，可追溯和回滚
- AI 在每次 CR 时学习新模式，定期建议规范更新

**具体维护流程**：
```
每次 CR 完成
    ↓
AI 分析发现的新模式 / 规范偏离
    ↓
生成 REVIEW_STANDARDS.md 的建议更新
    ↓
Reviewer 审核建议
    ↓
手工 merge 或拒绝（1-2 周一次集中更新）
    ↓
自动提交到 git，记录版本历史
```

### 10.4 推广策略
- ✅ **决策**：短期团队试用，验证价值后推广

**推广分阶段**：

| 阶段 | 时间 | 对象 | 目标 |
|------|------|------|------|
| Phase 1（试点） | 2-3 周 | 2-3 个核心开发者 + Reviewer | 收集反馈，优化规范和检测规则 |
