## 🎯 部分 1：部署完成检查清单

### Pre-Deployment（部署前）

- [ ] **理解需求**
  - [ ] 确认你的工作流（周一-周五的具体时间点）

  - [ ] GitLab/Bitbucket 的服务器地址（或使用官方地址）

- [ ] **TypeScript 配置**
  - [ ] `tsconfig.json` 已创建
  - [ ] `package.json` 中有所有必需的依赖

### Validation（验证）

  - [ ] 运行 `npx ts-node validate-config.ts` 成功
  - [ ] VCS 连接测试通过 ✅

## 🔄 部分 2：扩展路线图

### Phase 1：MVP（当前 ✅ 已完成）

```
目标：最小可用产品 - 自动生成基本的迭代报告

功能：
  ✅ GitLab 和 Bitbucket 支持
  ✅ 自动获取合并的 PR/MR
  ✅ 自动统计代码改动（文件、新增、删除）
  ✅ 生成本地 Markdown 报告
  ✅ CLI 命令行接口

好处：
  ⏱️  从 30 分钟 → 2 分钟（节省 28 分钟/版本）
  ✅ 100% 自动化，零遗漏
  📊 一致的报告格式
  🔍 完整的代码改动历史

当前状态：
  ⏳ 等待你提供 VCS 配置信息进行验证
```

### Phase 2：需求系统集成（计划中 ⏳）

```
目标：自动获取需求信息，不再手动映射

前提条件：
  • 你的自建需求系统有 API
  • 能够提供 API 文档和示例

开发内容：
  - RequirementSystemAdapter（需求系统适配器）
  - 从 PR 描述自动提取需求号
  - 调用需求系统 API 获取需求详情
  - 在报告中展示需求状态、责任人等

预期收益：
  ✨ 无需手动输入需求
  📋 自动生成需求清单
  🔗 需求与 PR 自动关联
  📊 需求完成度统计

预计工作量：1-2 天（取决于需求系统 API 复杂度）

开始条件：
  当你的需求系统有 API 后
  或提供 API 文档和示例请求
```

### Phase 3：文档系统集成（计划中 ⏳）

```
目标：自动上传报告到文档系统，不再手动创建文档

前提条件：
  • 文档系统有 API（或 MCP）
  • 能够提供访问信息

支持方案：
  Option A：腾讯文档 API（如果开放）
  Option B：自建文档系统 API
  Option C：MCP（如果团队引入）

开发内容：
  - DocumentPublisher（文档发布器）
  - 将 Markdown 转换为目标格式
  - 自动上传到文档系统
  - 返回文档链接

预期收益：
  📄 报告自动出现在文档系统
  🔗 可分享的文档链接
  📚 版本报告统一管理
  🕐 可追溯的历史版本

预计工作量：1-2 天（取决于文档系统 API）

开始条件：
  当文档系统有 API 或 MCP 支持后
```

### Phase 4：机器人通知集成（计划中 ⏳）

```
目标：自动通知团队，报告生成时立即发消息

前提条件：
  • 自建机器人有 Webhook
  • 提供 Webhook URL 和消息格式规范

开发内容：
  - CustomRobotNotifier（机器人通知器）
  - 将报告摘要转换为消息格式
  - 通过 Webhook 发送到机器人
  - 支持多种消息格式（JSON/Text/Markdown）

预期收益：
  🤖 报告生成时自动通知
  💬 团队即时获知版本信息
  📊 摘要统计在消息中展示
  🔔 可配置的通知时机

预计工作量：1 天

开始条件：
  当你提供 Webhook URL 和消息格式规范后
```

### Phase 5：多仓库支持（计划中 ⏳）

```
目标：同时处理多个 GitLab/Bitbucket 仓库的合并报告

场景：
  • 前端有多个仓库
  • 分别需要合并各仓库的 PR 到一个统一报告

开发内容：
  - 支持配置多个 VCS 实例
  - 同时获取多仓库的 PR 信息
  - 合并生成综合报告
  - 显示每个仓库的贡献比例

预期收益：
  📊 一份报告覆盖整个版本的所有改动
  🏢 跨仓库统计代码改动
  👥 按仓库展示参与者
  🔀 分清各仓库的职责

预计工作量：2-3 天

开始条件：
  当需要支持多仓库时
  提供所有仓库的配置信息
```

### Phase 6：高级分析（计划中 ⏳）

```
目标：提供更深层的分析和洞察

功能：
  1. 代码质量分析
     - 识别风险改动（删除大量代码）
     - 识别复杂改动（修改众多文件）

  2. 影响范围分析
     - 按模块/包统计改动
     - 识别高风险模块

  3. 历史对比分析
     - 与上个版本对比
     - 显示改动趋势

  4. 性能影响估计
     - 识别性能相关改动
     - 提出测试建议

  5. 安全风险评估
     - 识别安全相关改动
     - 提出审查重点

预期收益：
  🎯 一目了然的风险点
  📈 版本改动趋势
  ⚡ 性能影响预测
  🔒 安全审查提示

预计工作量：3-5 天

开始条件：
  需要这些高级功能
  提供相应的数据源（如代码库结构、性能基准等）
```

### Phase 7：集成到 CI/CD（计划中 ⏳）

```
目标：报告生成完全自动化，融入 CI/CD 流程

方案：
  Option A：GitHub Actions（如果使用 GitHub）
  Option B：GitLab CI（如果使用 GitLab）
  Option C：自建 CI 系统

开发内容：
  - 编写 CI/CD 配置文件
  - 配置定时运行或手动触发
  - 集成报告上传和通知
  - 构建完整的发布流程

预期收益：
  🚀 一键发起报告生成
  ⏱️  定时自动生成（如每周四中午）
  🔗 与发布流程完全融合
  📊 报告自动存档

预计工作量：1-2 天

开始条件：
  团队确认使用的 CI/CD 平台
```

## 📊 部分 3：功能优先级矩阵

```
          高价值
            ▲
            │
     Phase 2 │ Phase 3    Phase 4
    (需求系) │ (文档)     (通知)
     高优先  │ 中优先     低优先
            │
            ├─────────────────────► 实现复杂度
            │ Phase 1   Phase 5
            │  (MVP)    (多仓)
            │  已完成   中复杂
            │
          低价值
```

**优先级说明**：

1. **第一优先** (Phase 1 - 已完成)
   - MVP 功能已实现
   - 可立即部署使用

2. **第二优先** (Phase 2 - 需求系统)
   - 当需求系统有 API 时立即实现
   - 能消除最大的手工工作量

3. **第三优先** (Phase 3 - 文档系统)
   - 当文档系统有 API 或 MCP 时
   - 提升报告的可达性

4. **第四优先** (Phase 4 - 机器人通知)
   - 当需要实时通知时
   - 相对低成本的增强功能

5. **可选** (Phase 5-7)
   - 当需要这些功能时再实现
   - 不影响 MVP 的使用

## 🎓 部分 6：学习和扩展指南

### 如果你想深入理解代码

```
推荐阅读顺序：

1. adapters/vcs-adapter.ts
   ├─ 理解 VCSAdapter 基类设计
   ├─ 学习 GitLab/Bitbucket API 的区别
   └─ 学习如何添加新的 VCS 支持（如 GitHub）

2. agents/release-report-agent.ts
   ├─ 理解 Agent 的核心逻辑
   ├─ 学习数据流处理（PR → 统计 → 报告）
   └─ 学习 Markdown 生成

3. cli.ts
   ├─ 理解命令行参数处理
   ├─ 学习环境变量加载
   └─ 学习错误处理

4. validate-config.ts
   ├─ 理解配置验证流程
   └─ 学习如何编写 validation 脚本
```

### 如果你想添加新功能

```
添加新的 VCS 支持（如 GitHub）:

1. 在 vcs-adapter.ts 中
   ├─ 创建 GitHubAdapter 继承 VCSAdapter
   ├─ 实现 getMergedPRs() 方法
   ├─ 实现 getFileStat() 方法
   └─ 在 VCSFactory 中注册新的类型

2. 更新 CLI 参数处理

3. 更新文档和 .env.example

4. 添加单元测试（如适用）

预计时间：2-3 小时（取决于 API 复杂度）
```
