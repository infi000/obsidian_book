## 1️⃣ 架构图 (Architecture Diagram)

**文件**: `迭代报告Agent-架构图.canvas`

### 展示内容

整个系统的**分层架构**，包括：

```
┌─────────────────────────────────────┐
│   CLI 接口层 (cli.ts)               │ ← 环境变量加载、参数验证、输出
├─────────────────────────────────────┤
│   业务逻辑层 (ReleaseReportAgent)   │ ← 核心算法
├─────────────────────────────────────┤
│   VCS 适配器层 (vcs-adapter.ts)     │ ← GitLab/Bitbucket 适配
├─────────────────────────────────────┤
│   外部系统 (GitLab / Bitbucket)     │ ← API 调用
├─────────────────────────────────────┤
│   输出 (Markdown 报告文件)          │ ← 最终结果
└─────────────────────────────────────┘
```

### 关键点

- **分层清晰**：各层职责明确
- **解耦设计**：业务逻辑与 VCS 细节分离
- **易于扩展**：添加新 VCS 只需实现一个适配器

### 何时使用

- 理解系统架构时
- 规划功能扩展时
- 向团队说明系统设计时

## 2️⃣ 核心工作流程 (Workflow Diagram)

**文件**: `迭代报告Agent-核心工作流程.canvas`

### 展示内容

Agent **从启动到完成**的整个工作流程（9 步）：

```
START
  ↓
第1步：加载环境变量
  ↓
第2步：验证配置
  ↓ (决策)
  ├─→ ❌ 错误? → 输出错误信息 → EXIT
  │
第3步：初始化 VCS 适配器
  ↓
第4步：获取合并的 PR/MR
  ↓
第5步：遍历每个 PR，统计改动
  ↓
第6步：聚合所有数据（求总和）
  ↓
第7步：生成 Markdown 报告
  ↓
第8步：保存到文件
  ↓
第9步：输出统计信息
  ↓
END ✅
```

### 关键特性

- **顺序清晰**：易于理解执行步骤
- **错误处理**：显示错误分支
- **性能标注**：标注每步耗时

### 何时使用

- 跟踪 Agent 的执行过程
- 理解何处可能出现错误
- 优化性能的关键点在哪

## 3️⃣ 数据流转图 (Data Flow Diagram)

**文件**: `迭代报告Agent-数据流转图.canvas`

### 展示内容

**数据从输入到输出**的完整转换过程：

```
INPUT: 环境变量
  ↓
转换 → VCSConfig
  ↓
处理步骤1: getMergedPRs()
  返回 → MergedPR[]
  ↓
处理步骤2: 遍历统计 FileStat
  累加 → FileStat (总计)
  ↓
处理步骤3: 生成 Markdown
  ↓
OUTPUT: Markdown 报告文件
```

### 数据结构详解

```typescript
// 输入
VCSConfig {
  type, baseUrl, token, projectId
}

// 中间数据
MergedPR[] {
  id, title, author, branch, webUrl
}

FileStat {
  files: 45
  additions: 2340
  deletions: 1200
  commits: 5
}

// 最终数据
ReleaseReport {
  version, totalPRs, totalFiles
  totalAdditions, totalDeletions
  prs: MergedPR[]
}

// 输出
Markdown 文本
```

### 何时使用

- 理解数据如何转换
- 调试数据问题
- 扩展数据处理逻辑

## 💡 深入理解

### 从架构图看设计原则

```
✅ 分层明确
  • 接口层：对外交互
  • 业务层：核心逻辑
  • 适配层：多态支持

✅ 解耦设计
  • 业务逻辑与 VCS 无关
  • 易于扩展新 VCS
  • 易于单元测试

✅ 单一职责
  • 每层只做一件事
  • 易于维护和修改
```

### 从流程图看执行过程

```
关键的错误检查点：
  第2步验证配置
  → 90% 的错误在这里被发现

关键的性能点：
  第4步获取 PR（500ms）
  第5步统计改动（1-5s）
  → 这两步是耗时的

关键的业务逻辑：
  第6步聚合数据
  第7步生成报告
  → 这是核心算法
```

### 从数据流转看数据变化

```
输入 (配置) → 业务处理 → 输出 (报告)

关键的转换：
  VCSConfig
    ↓ (API 调用)
  MergedPR[] + FileStat
    ↓ (数据聚合)
  ReleaseReport
    ↓ (格式化)
  Markdown 文件

每一步的输入/输出都定义清晰
→ 易于理解数据流
→ 易于调试问题
```
